## Decisions worth recording

**Enforced invariants instead of documented ones.** §5.1 states that all
timestamps are timezone-aware UTC and all prices are integer cents. Both are
enforced in `__post_init__` and rejected loudly rather than left to convention.
A naive datetime raises when compared against an aware one, or silently compares
under an unstated local offset; since point-in-time correctness (§6.1) is
entirely a claim about timestamp ordering, an ambiguous timestamp is an unsound
backtest. The same reasoning applies to `rules_hash`: `Market` is versioned
rather than updated in place, the hash is what separates one version from the
next, so a hash that does not match its text would silently merge two versions.
`Market.__post_init__` recomputes it and refuses the mismatch.

**Literal types instead of `str`.** §5.1 writes `taker_side: str` with the
allowed values in a comment (`"yes" | "no"`), and likewise for `outcome` and
`strike_type`. Those are spelled as `Literal` aliases, which encodes the
comment's own intent and lets `mypy --strict` catch a typo at the call site.
The runtime representation is unchanged — they are still strings.

**Book derivation lives in `types.py`.** The venue-native form (resting YES
bids, resting NO bids) is stored as recorded, and `BookSnapshot.two_sided()`
derives the canonical view with `TwoSidedBook.to_venue()` as its inverse. This
is representational, not strategic, so it does not violate "no business logic".
It is centralised because §5.1 flags the failure mode explicitly: a resting NO
bid at `n` is a YES ask at `100 - n`, and inverting that reflection flips the
sign of the entire P&L while leaving a book that still looks entirely plausible.
The round trip is asserted both on a worked example and as a hypothesis property
over random books.

**CI is a separate path-filtered workflow.** The host repository aggregates its
blocking checks through `blocking-ci.yml`, which calls reusable workflows.
Reusable workflows cannot carry path filters, so registering pmtrade there would
run a Python lint/type/test job on every unrelated pull request. Instead
`.github/workflows/pmtrade.yml` triggers on `pmtrade/**`. The tradeoff is real
and stated here rather than buried: pmtrade's checks are **not** part of the
repository's required merge gate, so a pmtrade change can merge with this
workflow red unless someone looks. If pmtrade becomes a first-class part of this
repository, move it into `blocking-ci.yml` and accept the per-PR cost.

**`uv sync --frozen`, not `uv sync`.** CI installs exactly what `uv.lock` pins
and fails rather than re-resolving, so a backtest run months from now resolves
to the same numeric libraries. Reproducibility of results is the whole point of
§10.

## What I am uncertain about

1. **Whether `pmtrade/` belongs in this repository at all.** It is a Python
   research subproject grafted into a Rust/TypeScript monorepo whose `AGENTS.md`
   is entirely about `codex-rs`. Nothing here conflicts with the host — the
   repository's formatter only touches `sdk/python` and `scripts`, and Bazel
   sees no targets under `pmtrade/` — but the two projects share no reason to
   live together. A standalone repository would be the natural home.

2. **`CLAUDE.md` is committed through a gitignore override.** The host
   repository's root `.gitignore` excludes `CLAUDE.md` at any depth, treating it
   as a stray agent-tool file. BLUEPRINT §3 requires it at the project root and
   defers to it wherever the two documents conflict, so `pmtrade/.gitignore`
   re-includes it with `!CLAUDE.md`. Git permits this because the parent pattern
   matches a file rather than a directory. It works, and it is commented at the
   negation, but it is a rule of the host repository being deliberately stepped
   around — worth a second opinion, and another argument for uncertainty 1.

3. **Dependency surface is declared but unexercised.** `polars`, `duckdb`,
   `httpx`, `websockets`, `lightgbm` and `scikit-learn` are pinned in the lock
   because §3 names them as the stack, but M0 imports none of them. In
   particular `disallow_any_unimported = true` is currently vacuous; the first
   milestone that actually imports these will discover which of them ship type
   information and which need a documented exception.

4. **Price bounds are inclusive of 0 and 100.** A binary contract settles at
   those values, so they are legal marks, but Kalshi only accepts orders
   strictly between them. If M1 finds the venue never emits a book level at 0 or
   100, tightening the validation would catch a class of parsing bug that the
   current bounds let through.

5. **`configs/` is empty and therefore uncommitted.** §3 lists `record.yaml` and
   `backtest.yaml`; git does not track empty directories and writing placeholder
   configs would be business logic. M1 and M6 create them.

6. **100% coverage on M0 proves very little.** The bar is enforced and met, but
   `types.py` is dataclasses and validation, which is the easiest code in the
   project to cover and the least likely to hide a bug that matters. Line
   coverage will stay easy to hit and increasingly uninformative through
   `store/` and `research/backtest/`, where CLAUDE.md's "tests before
   implementation" rule is doing the real work. Treat the number as a floor that
   catches untested modules, not as evidence the code is correct.

## Blocked, and why

M1 cannot be attempted in the environment this was built in: outbound requests
to `api.kalshi.com` and `api.elections.kalshi.com` are refused by network policy
(403 on CONNECT). M1's acceptance criterion is "every active economics series
retrieved", which is unverifiable without the live API, and §9 requires that
every endpoint, channel, and auth detail be checked against `docs.kalshi.com`
before implementation. Writing the client blind would produce code that cannot
be run, tested, or verified — precisely what §4's milestone gate exists to
prevent.

## Open questions still outstanding

None of BLUEPRINT §12's four questions were resolved, and none of them blocked
M0. Questions 1 (order book depth access) and 3 (account eligibility) must be
answered before M2; question 2 (intraday ZQ data) before M9. Question 4 (whether
to record a higher-frequency domain in parallel as sample-size insurance) is
worth answering before M2 rather than after, because it is a decision about what
to start recording, and recording that did not happen cannot be backfilled.

Question 1 is now a harder question than the blueprint framed it. CLAUDE.md hard
rule 2 states that M1–M10 use only public, unauthenticated market data
endpoints, with no credentials in the repository in any form. The blueprint's
recommended option (b) — an unfunded account with a read-only API key in an
environment variable — is therefore not a preference to weigh but a direct
amendment to a hard rule, needing explicit approval before any code assumes it.
Until that approval exists, option (a), polling the public REST orderbook
endpoint on an interval, is the only implementable path, and M2's design should
assume it.

CLAUDE.md hard rule 6 also adds work that BLUEPRINT §4 places at M5: the import
test forbidding `strategy/`, `research/models/` and `live/` from importing raw
or normalised stores. Nothing in M0 can violate it — those packages contain only
docstrings — but the test itself is M5's, and it is recorded here so it is not
lost.
